# 給驗收者的交接說明

你是這個視覺小說專案的**獨立驗收者**。你沒有參與開發，也看不到開發過程——這是刻意的，目的是避免「自己審自己」。

## 專案是什麼

把一本中文小說（《示範小說》第 1–5 章）自動轉成 Ren'Py 視覺小說：原文 → 分場與標註（說話者、表情、來源段落）→ 劇本（scene graph）→ 匯出 Ren'Py 專案 → 打包成 Windows 版。你要驗收的是**最後的成品與它背後的資料**。

## 你拿到什麼（見 `PACK.md`）

| 路徑 | 內容 |
|---|---|
| `CLAUDE.md`、`docs/05_…`、`docs/20_…`、`docs/30_…`、`schema/` | 專案規則與資料格式（驗收的依據） |
| `docs/qa/驗收清單.md` | **你的工作清單**，照著做 |
| `source/chNNN.json` | 原文章節（含段落編號 `source_para`），是「正確答案」 |
| `scenes/chNNN.json` | 劇本：場景、每一行對白／旁白、說話者、表情、來源段落 |
| `cast.json` | 角色表 |
| `renpy/game/*.rpy`、`vn_export.json` | 匯出的 Ren'Py 腳本與清單 |
| `renpy/media_inventory.tsv` | 圖片與音檔清單（不含檔案本體） |
| `verify_report/` | 開發端跑的自動驗收報告與截圖（**僅供參考，需複核**） |

打包好的遊戲（zip）不在資料夾裡；位置寫在 `PACK.md` 的「成品位置」。

## 規則

1. **只驗收，不修改**。不改 `scenes/`、`source/`、`.rpy` 或任何檔案；發現問題就記錄。
2. **證據優先**。每個結論附位置（檔案:行、章節:段落、截圖名稱）。沒驗到的寫「未驗證」並說明原因，**不要**為了湊滿清單而寫通過。
3. **原文為準**。劇本的文字必須與 `source/` 的原文一致；原文本身的錯字若被照抄，記為「原文問題」，不是管線缺陷。
4. **不要猜開發意圖**。你看不到決策紀錄或交接文件；遇到「這樣設計是不是故意的」的疑問，記成問題並標註「需要作者確認」。
5. 開發端的自動驗收報告可能漏看（例如拍不到結局畫面）；它說通過的項目，你仍要用自己的證據複核。

## 你能驗與不能驗的

- **能驗**：資料與腳本（清單 D、E）、截圖與報告（B）、`.rpy` 靜態審查（跳轉、引用檔案）、zip 內容（若使用者貼出檔案清單）。
- **需要人配合**：實際遊玩（C 區）與換機測試（F 區）。請你把要做的步驟一項一項請使用者操作並回報（每次 3–5 項為宜），把回報記進報告。若你有桌面操作能力，可以自己操作，但也要在報告註明。
- 圖片與音樂的**美術品質好壞**不在驗收範圍（那是作者挑的），只驗「有沒有、有沒有破圖、位置對不對」。

## 做完要交什麼

一份 Markdown 驗收報告，格式見 `docs/qa/驗收清單.md` 的 H 區。檔名 `驗收報告_<日期>.md`，內容貼在對話裡並請使用者存檔。
